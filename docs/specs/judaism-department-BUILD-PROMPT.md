# פרומט לסוכן הבונה — מודול מחלקת יהדות

> העתק את הטקסט שמתחת לקו כפרומט לסוכן שיבנה את המודול. הוא מפנה לאפיון המלא ומגדיר כללי עבודה, סדר, ואישור.

---

אתה בונה את **מודול מחלקת היהדות** במערכת CampusSystem (Next.js 14 App Router · TypeScript · Supabase).

**קרא קודם, לפני שורת קוד אחת:**
1. `CLAUDE.md` בשורש — כללי העבודה מחייבים (אין לסטות מהאפיון בלי לסמן; דוחות אמת; בספק לשאול; חוקי Supabase `PostgrestBuilder`).
2. `docs/specs/judaism-department-module.md` — האפיון המלא. הוא מקור האמת ל*מה* לבנות.
3. **סעיף 1 באפיון ("רקע טכני")** — קריטי: רוב התשתית כבר קיימת. אל תבנה מחדש. אמת כל טבלה/פונקציה שהאפיון מזכיר מול הקוד האמיתי לפני שאתה מרחיב אותה.

**⭐ עקרון-על (הודגש שוב ושוב ע"י הלקוח): הכל חייב להיות תמיד ניתן לשינוי.** אל תקודד קשיח שום נתון תוכן — מסלולים, שמות רמות/קבוצות, סוגי התראות, תבניות, מכסות, מחירים — כולם data/config עם CRUD מ-UI. עדיף טבלת-עזר על `CHECK (... IN ...)` קבוע. כל "ברירת מחדל" היא הצעה שאפשר לשנות, וגם מקור ההצעה (התבנית) ניתן לעריכה. ראה סעיף 0.3 באפיון.

**עקרונות ביצוע:**
- **בנה לפי השלבים** שבסעיף 7 באפיון (שלב 1 → 2 → 3). אל תתחיל שלב לפני שקודמו עובר אימות. בתוך שלב, סדר: מיגרציה → API → UI → i18n → טסטים.
- **הרשאות fail-closed** בכל route חדש (`hasEducationPrivilege` / `canManageUnit`). הפרדת הסמכויות משה⇄חנה נאכפת בשרת, לא רק ב-UI.
- **מיגרציות**: אידמפוטנטיות, `IF NOT EXISTS`, בסגנון המיגרציות הקיימות (הערות, `set_updated_at()`). הן **מיושמות ידנית** ע"י בעל המערכת — אל תריץ SQL על פרודקשן. רכז כל מיגרציה חדשה ברשימה בסוף כל שלב.
- **i18n / RTL / dark-mode** לפי סעיף 8 באפיון: כל מחרוזת ב-`messages/{he,ru,en}.json` (מפתחות שטוחים, כל 3 השפות — אמת parity); `localISODate()` לבוררי תאריך; טוקני צבע; `marginInlineStart`.
- **אימות בסוף כל שלב** (חובה, אל תדווח "בוצע" בלי להריץ): `npx tsc --noEmit` · `npx next lint` · `npx vitest run` · `npx next build`. אם משהו נכשל — תקן או דווח מפורש, אל תסתיר.

**כשאתה נתקל ב-❓ פתוח או ⚙️ הנחה באפיון:**
- על **❓ פתוח** (החלטת לקוח) — **עצור ושאל** את בעל המערכת. אל תנחש. הרשימה בסעיף 6 באפיון.
- על **⚙️ הנחה** — פעל לפיה, אבל אם היא נראית שגויה בהקשר הקוד — עצור, הסבר, ובקש אישור (כמו ב-`CLAUDE.md`).

**דיווח:** בסוף כל שלב, דוח בעברית עם: מה נבנה, אילו מיגרציות בעל-המערכת צריך להריץ, אילו ❓ נותרו פתוחים, ותוצאות ה-4 בדיקות האימות. אם סטית מהאפיון — זה בראש הדוח, לפני "בוצע".

**עבודת git:** פתח על ענף ייעודי, commit תיאורי בסוף כל שלב, push לענף. אל תפתח PR בלי בקשה מפורשת.

התחל משלב 1. מבנה 8 קבוצות הקודש וקטלוג המסלולים כבר **נסגרו** ע"י הלקוח (ראה 1.3 ו-1.4 באפיון) — בנה לפיהם. ה-❓ שנותרו פתוחים (סעיף 6 באפיון) אינם חוסמים את שלב 1: מכסת שעות (שלב 2) ואחראי הכספים (שלב 3) — כשתגיע אליהם, פעל לפי ⚙️ ברירת המחדל שבאפיון ובקש אישור אם עדיין פתוח.
